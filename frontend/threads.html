LLM 调用线程模型

谁在哪个线程调模型 · 谁会阻塞用户 · 怎么防串话

管理台

HTTP 层

waitress 生产服务器，8 个 worker 线程（THREADS=8）。每个请求占一个 worker；聊天与管理台、搜索互不排队。

对话串行锁

CHAT_LOCK 让 /api/chat 同时只有 1 个在跑，防止两个请求交叉写会话历史；其他接口照常并行。

后台抽取线程

记忆抽取是 daemon 线程，在回复返回之后才跑，EXTRACT_LOCK 防重入。永远不占用户的等待时间。

一次提问的时间线（横轴 = 时间）

worker 线程
① 检索+记忆注入（本地，毫秒级）
② llm 工具循环 1~4 次 = 回答本体
③ 返回回复 ✓
daemon 后台线程
④ 记忆抽取（独立 llm.chat，不阻塞任何人）

worker 在 ③ 就释放了；④ 在另一个线程继续跑。下一轮提问最多和 ④ 排队错开，永不互相等。

三类 LLM 调用对比

为什么以前会出现"记忆占用主线程"？

旧版（同步写法）

② 回答 LLM（用户在等）
③ 记忆抽取 LLM ← 用户也在等！
同一个 worker 线程串行做完才返回，每 24 条消息那次回答多等一次完整 LLM 往返

新版（daemon 线程）

② 回答 LLM → 返回 ✓
③ 抽取在后台跑，用户无感
